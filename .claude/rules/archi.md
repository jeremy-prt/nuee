# Architecture Tauri + Vue

Même logique que l'archi Nuxt : depuis un bouton, on retrouve vite la commande Rust puis le service qui fait le travail. Ni repository, ni DTO, ni injection de dépendances. Noms de fichiers en anglais, commentaires en français.

| WebDev / Nuxt | Ici |
|---|---|
| Classe et ses méthodes (`server/services/XxxService.ts`) | `src-tauri/src/services/<domaine>.rs` : `struct XxxService` + `impl` |
| Route API d'un bouton (`server/api/`) | `src-tauri/src/commands/<domaine>.rs` : commande mince |
| `$fetch('/api/...')` | `src/ipc/<domaine>.ts` : wrapper typé autour de `invoke` |
| Schéma Zod partagé (`shared/schemas/`) | struct Rust, type TS généré par ts-rs |
| Variable globale (`gcl...`) | store Pinia |
| Page | `src/views/XxxView.vue` |

```
src/
  views/                    # 1 fichier = 1 écran ; bandeau `// ===== Initialisation =====` pour l'init
  components/<domaine>/     # <Domaine>Xxx.vue
  components/ui/            # UiXxx.vue : nos briques stylées, reka-ui (headless) dessous
  composables/              # useXxx : données réactives + chargement, une instance par appel
  stores/                   # Pinia, un store par domaine, un seul exemplaire partagé
  ipc/                      # seul dossier qui importe @tauri-apps/api
    <domaine>.ts            # 1 fonction = 1 commande Rust
    bindings/               # généré par ts-rs, jamais édité à la main
  i18n/                     # createI18n + choix de la langue au démarrage
    locales/<langue>.ts     # en.ts fait référence, les autres finissent par `satisfies typeof en`
  utils/                    # fonctions pures ; shortcuts.ts = tous les raccourcis clavier ; `*.worker.ts` : Web Worker qui n'appelle que ces fonctions (effets de l'image de fond)
  assets/css/main.css       # Tailwind 4 : jetons de couleur dans @theme, pas de tailwind.config.js
src-tauri/src/
  main.rs                   # n'appelle que nuee_lib::run()
  lib.rs                    # Builder : plugins, manage(XxxService), generate_handler!
  error.rs                  # AppError (thiserror), sérialisé en { kind, message }
  menu.rs, window.rs        # réglages natifs au démarrage : menu macOS, taille de la fenêtre
  commands/<domaine>.rs     # valider, appeler le service (ou la lib si c'est une ligne), répondre
  services/<domaine>.rs     # la logique métier ; un domaine à plusieurs fichiers devient services/<domaine>/mod.rs
  utils/                    # helpers techniques (chemins, env shell)
```

## Pont Vue <-> Rust

- F12 ne traverse pas `invoke` : le nom de commande est une chaîne. Pour s'y retrouver, même nom de domaine partout (`ipc/session.ts` -> `commands/session.rs` -> `services/session.rs`) et commande nommée `<domaine>_<action>` (`session_start`) : un grep sur ce nom trouve les deux côtés.
- Composants, composables et stores n'appellent jamais `invoke` : ils passent par `src/ipc/`.
- La struct Rust est la source de vérité des types : `#[derive(Serialize, Deserialize, TS)]`, `#[serde(rename_all = "camelCase")]` sur tout ce qui traverse l'IPC. ts-rs exporte pendant `cargo test` ; le dossier de sortie se fixe avec `TS_RS_EXPORT_DIR` dans `src-tauri/.cargo/config.toml`.
- Flux continu (sortie d'agent, logs) : un `tauri::ipc::Channel<T>` passé en paramètre de la commande. `emit` seulement pour les notifications rares. Côté Vue, accumuler dans un `shallowRef` et pousser une fois par frame (`requestAnimationFrame`), sinon la réactivité rame.

## Rust

- Commandes `pub` dans leur module, `async` dès qu'elles font des I/O, retour `Result<T, AppError>` dès qu'elles peuvent échouer. Un seul `generate_handler!` dans `lib.rs` : un second appel écrase le premier.
- Pas de `unwrap()` / `expect()` hors démarrage : on remonte une `AppError`.
- État : `std::sync::Mutex` par défaut, celui de tokio seulement si le verrou doit traverser un `.await`. Jamais de verrou tenu pendant un `.await`. Pas d'`Arc` autour de ce qu'on passe à `manage()`, Tauri l'enveloppe déjà.
- Process enfants (CLI d'agents) : le front envoie un id d'agent et des options, jamais une ligne de commande. Rust construit la commande depuis une liste connue, garde le PID et tue par ce PID (`kill_on_drop`).
- Lancée depuis le Finder, l'app n'a pas le PATH du shell : résoudre les binaires d'agents via un login shell.
- Outil absent (Claude Code, gh) : Nuée ne l'installe jamais (choix de Jérémy), « Installer » ouvre sa page officielle par `install_open` (`services/install.rs`, adresse choisie par Rust, ouverte côté Rust hors scope de la capability). En debug, `NUEE_HIDE_BINARIES` fait renvoyer `None` à `find_binary` et masque aussi un chemin choisi à la main.
- macOS : notifications et pastille du Dock par `UNUserNotificationCenter` (`services/notification.rs`), pas `tauri-plugin-notification` (son `NSUserNotification` est refusé par macOS 27) ; lancement au démarrage par `auto-launch` en SMAppService, pas `tauri-plugin-autostart` (son LaunchAgent range l'app en tâche de fond). Les deux exigent l'app empaquetée et signée avec `signingIdentity: "-"` (sinon l'identifiant de signature ne correspond pas et macOS refuse sans demander).
- Brancher un agent (Codex, Cursor...) : une variante dans `AgentKind`, un `Driver` dans `services/agent/<agent>.rs` (arguments de la CLI, sonde qui liste ses modèles, traduction de sa sortie en `AgentEvent`), son nom et sa commande dans `src/utils/agents.ts` (en le retirant de `upcomingAgents`), son logo dans `assets/agents/` et `SettingsAgentLogo`. Un process par chat gardé ouvert (`services/agent/session.rs`) : messages et interruption écrits sur stdin, relancé avec `--resume` si le mode, le modèle, l'effort ou le dossier change, arrêté après 5 min sans tour. Il démarre dès le focus du champ de saisie (`agent_warm`).
- Réglages > Agents : la liste sur la page, les réglages de chaque agent dans sa sous-page (`settingsDetail` = son `AgentKind`). `stores/agents.ts` garde, par agent, l'activation, le chemin choisi à la main et les réglages de départ d'un nouveau chat (repris par `conversations.blank`). Statut par `agent_probe`, comme T3 Code : la CLI lancée sans tour répond à `initialize` (version, compte, modèles) puis `get_usage` (quotas ; `skip_behaviors`, sinon elle parcourt tout l'historique local). Jamais de lecture du jeton ni du Trousseau. Dernière version sur npm (`dist-tags`, selon `autoUpdatesChannel` ou le cask Homebrew), mise à jour par `claude update`. Un chemin choisi à la main doit se nommer comme l'agent, et sert ensuite à tous ses chats. Un tour qui contredit le compte affiché relance la sonde. Pendant un tour, les `rate_limit_event` du flux (événement `usage`) mettent les quotas à jour ; celui d'un modèle (Fable) n'y est pas nommé, la sonde donne son nom. Interrupteur Hooks : `hooks` dans `SessionSpec`, `--settings {"disableAllHooks":true}` quand il est coupé (tous les hooks, garde-fous compris) ; le changer relance le process au tour suivant.
- Réglages > Skills et MCP : config globale de Claude Code seulement (ceux d'un projet iront sur sa future page Projet, choix de Jérémy). Les interrupteurs de la liste ne valent que pour Nuée ; la sous-page d'un skill (`skill:<dossier>`) ou d'un serveur (`mcp:<nom>`) laisse choisir Nuée seulement ou Partout, repart sur Nuée à chaque ouverture et signale Partout en rouge (choix de Jérémy). Nuée seulement : gardé dans `stores/skills.ts`, envoyé dans `SessionSpec` (`skills`, `serversOff`) et passé en `--settings` ; un skill coupé partout peut y être rallumé, pas un serveur (`deniedMcpServers` s'additionne). Partout : `services/agent/settings.rs` écrit le `settings.json` (`skillOverrides` dont la clé est le nom du dossier, pas le `name:` du SKILL.md ; `deniedMcpServers`, seul réglage qui coupe un serveur de toutes ses portées), ordre des clés et droits gardés. Pas de création de skill à la main : « Nouveau skill » et « Modifier avec l'IA » (`composables/useSkillChat.ts`) ouvrent un chat dont Nuée affiche elle-même le formulaire (élément `command`, sans tour d'agent) ; la `ChatCommand` part avec la première réponse, Rust y ajoute les consignes de `services/agent/skill_writer.md` (tirées du skill `j-create-skill` de Jérémy) avec les vrais chemins. Formulation toujours identique (choix de Jérémy) : l'IA finit par un seul bloc `nuee-skill` (JSON) que `ChatSkillResult` met en forme ; le texte affiché vient de l'i18n, jamais de l'IA. Skills relus à chaque ouverture du menu « / » du composer ou de la page, pas de surveillance du dossier ; la CLI voit un skill créé sans relancer sa session. État des serveurs : la CLI lancée sans tour répond à `mcp_status`, redemandé jusqu'à ce qu'aucun ne soit en connexion et au moins 2 s (les serveurs de plugins arrivent tard). Les connecteurs du compte claude.ai sont écartés de la liste (choix de Jérémy). Connexion OAuth par `mcp_authenticate` une fois le serveur listé, jamais `claude mcp login` qui exige un terminal ; un serveur revenu est retenté dans les chats ouverts (`mcp_reconnect`). L'aperçu et l'éditeur d'un SKILL.md s'ouvrent dans le panneau de droite de `App.vue` (même poignée et largeur `layout.right` que celui des chats), jamais dans un panneau propre à la page.
- Réglages > Intégrations : GitHub par la CLI `gh` seulement, lancée par Rust (`services/github.rs`). Jamais sa config ni le Trousseau, jamais `gh auth token` (aucun jeton dans l'IPC, un log ou le disque), jamais `logout`, et `switch` seulement sur le bouton « Rendre actif » (il change gh dans tous les terminaux, d'où le refus d'un compte que gh ne liste pas comme utilisable). `gh auth status --json hosts` est lu même avec un code de sortie non nul ; `unknown flag: --json` = gh trop ancien, pas « déconnecté ». L'interrupteur d'un compte ne vaut que pour Nuée (`stores/integrations.ts`, clé `hôte/login`, tous activés par défaut). Page en cartes de services comme Réglages > Agents, sous-page `github` pour les comptes. Avatars : `https://github.com/<login>.png` lu par Rust sans jeton et passé en `data:` (la CSP n'autorise aucune image distante). Ajout d'un compte : `gh auth login --web` sans `--git-protocol` (gh l'écrirait pour tous les comptes) et sans terminal (stdin nul), qui écrit code et URL sur stderr sans attendre de touche ni ouvrir de navigateur ; Rust les passe par `Channel`, ouvre la page sur « Ouvrir GitHub » par `tauri_plugin_opener::open_url` (côté Rust, hors scope de la capability) et annule par le PID. Le compte ajouté devient l'actif de gh (comportement de gh, signalé dans l'interface).
- Connexion du compte d'un agent (`services/agent/login.rs`, `AgentLogin.vue`, dans l'erreur d'un message et Réglages › Agents) : `claude auth login` sans terminal ouvre la page de connexion et attend sur stdin le code `code#état` que la page affiche (pas de retour sur localhost, essayé). Rust garde l'adresse, le front envoie le code, Rust l'écrit sans le journaliser. Lancée sous `tauri dev` depuis un terminal, la CLI peut entourer l'adresse d'un lien OSC 8 : la couper au premier caractère de contrôle. Les process ouverts sans compte sont retirés une fois connecté.
- Mode Auto : les demandes d'autorisation passent par `--permission-prompt-tool stdio` (`control_request` `can_use_tool`) et s'affichent dans `ChatApproval` ; Rust garde les paramètres de l'outil pour les renvoyer avec l'accord. Pas de consigne système ajoutée à Claude : une phrase en anglais en fin de prompt le fait répondre en anglais.
- Message envoyé pendant une réponse (Réglages › Général) : en file côté front (`conversations.queue`, un par tour, retenue après un arrêt), ou `agent_steer` qui l'écrit sur stdin pendant le tour ; la CLI le lit à sa prochaine étape, dans le même tour (essayé). Refusé une fois `answered` reçu : il repasse en file. Limite d'utilisation : `rate_limit_event` au statut `rejected` donne l'événement `limited` ; le front renvoie un message à l'heure de remise à zéro, minuterie non persistée.
- Fin de tour en deux temps : `answered` dès que la réponse est complète (le front affiche « Terminé »), `turnEnd` quand l'agent a fini de ranger (résumé, hooks : plusieurs secondes). Un message envoyé entre les deux attend `turnEnd`. Après un arrêt, le texte coupé est rappelé à l'agent si son process est neuf (paramètre `recap`).
- Entre deux tours, la session garde le canal du dernier tour (`listener` dans `services/agent/session.rs`) : tâches de fond qui avancent, et tour que Claude rouvre seul quand l'une finit (`turnStart`). Le process n'est pas arrêté pour inactivité tant qu'une tâche tourne. Une requête qui attend sa réponse (rewind) passe par `Session::request`, la `control_response` est routée par son `request_id`.
- Flags de chat Claude non documentés, essayés sur la CLI : `--thinking-display summarized` (sans lui la réflexion arrive vide), `--replay-user-messages` (l'`uuid` de chaque message devient `agentId` sur l'élément `user`), `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=1` pour `rewind_files`, puis `rewind_conversation` (`target_message_uuid`, coupe tenue après `--resume`). `tool_use_summary` écarté exprès : un appel de modèle par série d'outils, l'app Claude ne l'affiche pas.
- Jauge de contexte : `control_request` `get_context_usage` (non documenté, même calcul que `/context`, répond sans tour ni connexion), pas la somme des `usage` du flux. Relevé à chaque `turnEnd` (id `nuee-context`, revient en événement `context`) et rendu par `agent_warm` ; gardé en base avec le chat (colonne `context`).
- Modèles et efforts : jamais codés en dur, l'agent installé les décrit (Claude : `control_request` `initialize`, lu une fois par lancement puis à chaque sonde de Réglages > Agents). L'interface montre toujours une valeur réelle (« Opus 5.5 », « Élevé »), jamais « par défaut ». Modes de permission : Bypass et Auto seulement (choix de Jérémy), passés en flag à chaque tour : ils priment sur la config Claude de l'utilisateur.
- Pièces jointes vers Claude : images en bloc base64 (la CLI redimensionne), autres fichiers en `@"chemin"` placé avant le message. Pas d'image en `@` : au-delà de ~3 Mo, elle est ignorée sans erreur.
- Chat sans projet : Rust le lance dans `<données de l'app>/scratch/<id du chat>`, supprimé avec le chat.
- Worktrees (`services/worktree.rs`, git toujours avec `-c core.fsmonitor=false`) : le sien, créé par `agent_send` au premier message dans `<données de l'app>/worktrees/<id du chat>` sur `nuee/<8 premiers caractères de l'id>` ; ou un worktree du dépôt rejoint par plusieurs sessions, créé dans la sous-page `worktrees:<id du projet>` (`worktrees/<id du projet>/<branche nettoyée>`). Le chemin est en base (`worktree_path`), jamais déduit de l'id ; un chemin venu du front n'est utilisé que s'il est dans `git worktree list`. Supprimer une session retire son propre worktree s'il est propre et que personne d'autre ne l'utilise ; supprimer un worktree est refusé s'il a des changements, et ses sessions repartent dans le dossier du projet (`--resume` y retrouve la conversation). La branche reste toujours, jamais `--force` (choix de Jérémy, comme T3 Code). Changer de branche après le premier message (`worktree_switch`) : le front donne l'id de la session, Rust retrouve son dossier. git répond dans la langue du système : ne jamais tester son message d'erreur, seulement les fichiers qu'il cite en retrait.
- Archives : colonnes `archived` et `archived_at`, la session quitte l'historique et la recherche, Réglages › Archives la restaure ou la supprime. Suppression automatique côté front (`workspace.purgeArchives`, au lancement puis toutes les heures, délai dans `stores/general.ts`) pour passer par `deleteChat` et son ménage (worktree, scratch, pièces jointes). La recherche des archives lit le texte des messages par `chat_archived_texts` (JSON des items lu en SQL). Dans l'interface, on dit « session », jamais « chat » (choix de Jérémy) ; seule exception, « Chat » nomme l'endroit des sessions sans projet (barre latérale, sélecteur des Archives). Les clés i18n et le code gardent `chat`.
- Historique : SQLite (`services/chat.rs`), une ligne par chat ; les messages sont un JSON que seul le front lit. Un chat n'entre dans l'historique qu'à son premier message (`started`). Fermer un onglet garde le chat (`layout.tabs` = onglets ouverts, `tabs` = tous les chats), sauf s'il n'a jamais servi ; sinon seule la corbeille de la barre latérale le supprime. Nouvelle colonne = nouvelle entrée dans `MIGRATIONS`, jamais une modif d'une entrée passée.

## Textes et langues

- Aucun texte d'interface en dur : la clé va dans `src/i18n/locales/en.ts`, puis traduite dans toutes les autres langues. vue-tsc bloque si une traduction manque, mais pas si `t('...')` cite une clé qui n'existe pas : la copier depuis `en.ts`.
- Aucun nom d'agent ni de service en dur dans un texte générique : `{agent}` (`agents[kind].name`), ou une formule neutre (« tes agents », « tes comptes connectés »). Nuée branchera plusieurs agents et services (choix de Jérémy) ; seule la page d'un service précis (GitHub) le nomme.
- `@` dans un texte i18n ouvre un lien vers une autre clé et casse la compilation : l'écrire `{'@'}`, dans une chaîne entre guillemets doubles.
- Traductions précompilées au build (`@intlify/unplugin-vue-i18n`, compilateur retiré du bundle) : un texte chargé à l'exécution (API, fichier) ne sera pas interprété en production.
- Langue du système : la commande Rust `system_locales`, jamais `navigator.language` (WebView2 renvoie toujours en-US). Dates et nombres : `Intl.*` avec la locale de vue-i18n, jamais `undefined`.
- Marges et positions en propriétés logiques Tailwind (`ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`) plutôt que gauche/droite : ça garde la porte ouverte aux langues écrites de droite à gauche.

## Interface

- Icônes : Hugeicons (comme monocode, choix de Jérémy), jamais lucide. Toujours par `components/ui/icons.ts`, qui importe chaque glyphe à part (`@hugeicons/core-free-icons/XxxIcon`, sinon tout le catalogue est chargé) ; une icône manquante s'y ajoute.
- Composants accessibles : reka-ui (headless) habillé dans `components/ui/`, jamais une lib de composants déjà stylés. Confirmation : `useDialogStore().confirm()`, jamais le `ask` natif ; message en bas de fenêtre : `useToastsStore().push()`.
- Infobulle sur un bouton qui ouvre un menu ou un popover reka : `UiTooltip` autour du `*Root`, jamais entre le `Root` et son `Trigger` (contexte Popper injecté au plus proche : le menu se cale sur l'infobulle et reste hors de l'écran, sans erreur). Voir `UiMenu`.
- `UiTooltip` autour d'un élément qui porte son état en `data-state` (radio, interrupteur) : le trigger de l'infobulle écrase cet attribut, styler l'état choisi sur `aria-checked`. Option grisée avec infobulle : l'enveloppe reçoit la souris, l'option est en `pointer-events-none` (voir `UiSegmented`).
- Mascottes de projets : SVG dans `src/assets/mascots`, `id` préfixés `__ID__` (remplacé par instance), couleurs seulement par les variables de `.mascot` (`--tint`... dans `main.css`), liste et ordre dans `mascotIds`. DA emoji météo (choix de Jérémy, après deux séries refusées : kawaii, puis brume floue).
- Couleurs uniquement via les jetons de `main.css` (`canvas`, `chrome`, `surface`, `popover`, `content`, `muted`, `stroke`, `selection`, `accent`, `signal`, `signal-text`, `on-signal`, `ring`, `stroke-focus`, `edge-hover`, `danger`, `success`, `warning`, `info`, `orange`, `skill`, `mention`). Pas de couleur nommée `base` : `text-base` est déjà la taille de texte de Tailwind. Badge d'état en version douce (`bg-signal/15 text-signal-text`, de même `success`, `warning`, `danger`) ; une étiquette sans état reste neutre (`bg-content/8 text-muted`).
- Focus et éléments choisis (carte sélectionnée, zone de dépôt survolée, pane actif) : `ring` (`signal` adouci, gardé à 3:1 sur les fonds), fond doux `bg-signal/15`, sans bordure colorée. Champ de saisie : sa bordure passe à `stroke-focus` (gris à peine plus clair, comme monocode), pas d'anneau.
- Le code ne déplace le focus que si le bouton validé au clavier disparaît (`event.detail === 0` sur le clic ; après une action async, `composables/useRefocus.ts` le passe à un voisin stable) : jamais après un clic souris, Échap ou un raccourci, sinon un anneau surgit ailleurs. Exceptions : la confirmation et la demande d'autorisation, qui prennent le focus en s'ouvrant.
- Barre latérale repliable : l'icône reste à 16 px du bord dans les deux états (rail `p-2` + item `px-2`, replié à 48 px), jamais de `justify-center`. Repli instantané, sans animation ; les libellés restent dans le DOM, masqués. Choix de Jérémy : dépliée, son bouton est dans la barre de titre ; repliée, il devient la première icône de la colonne.
- Boutons de colonne (barre latérale, panneau) : au-dessus du bord droit de leur colonne, sans fond « actif », seulement survol et infobulle. Le bouton de la barre latérale montre l'action (flèche gauche pour replier, droite pour déplier).
- Navigation : `stores/navigation.ts` choisit la vue centrale. Seule la vue `chats` a des onglets, l'historique des chats et les panneaux bas/droite ; Accueil, Issues, Notes, Réglages… sont des pages pleine largeur dans `views/`.
- Les onglets de la barre de titre démarrent au bord de la colonne centrale : `ShellTitleBar` additionne les largeurs des colonnes de gauche. Une nouvelle colonne à gauche doit entrer dans ce calcul.
- Barre de titre pleine largeur : une bordure verticale de colonne n'y monte que si elle ne croise pas les boutons de fenêtre macOS (calcul dans `ShellTitleBar`). Ce segment s'allume avec la poignée de la colonne (`data-edge` sur `ShellResizeHandle`, `data-title-edge` dans la barre, règle dans `main.css`) : renommer l'un casse le lien sans erreur.
- Transparence et flou : macOS seulement (classe `is-macos` posée au démarrage), Windows et Linux restent opaques. Fond d'une colonne : `bg-chrome` (cadre : barres, liste des chats, terminal, panneau de droite) ou `bg-surface` (le chat ou la page au centre), jamais une opacité en dur : le style de fenêtre choisi dans les réglages (`stores/appearance.ts`, `data-window` sur `<html>`) les rend transparents dans `main.css`.
- Thèmes (`utils/themes.ts`) : un thème fixe `--color-accent` et `--color-signal`. Bouton principal en `bg-accent text-canvas`, jamais `bg-content` : il doit suivre le thème. Ce qui signale un état (interrupteur allumé, non lu, badge « Actif », mise à jour dispo) : `signal`, jamais `accent` ; c'est l'accent d'un thème coloré, `#0A7AF2` dans un thème neutre comme Nuée, où l'accent est blanc (choix de Jérémy, comme monocode et T3 Code). En texte, `signal-text` (le signal éclairci, lisible en petit). Sur `signal`, le rond d'un interrupteur est `on-signal` : blanc, sombre sur Soleil (`darkOnSignal`) ; sur `accent`, le texte est `canvas`. Carte choisie : fond `bg-signal/15` sans bordure (choix de Jérémy). Les fonds d'éléments actifs passent par `bg-selection`, que le mode « Toute l'interface » teinte avec l'accent.
- Flou du bureau : commande `window_set_blur` (API privée `CGSSetWindowBackgroundBlurRadius`, comme monocode et Brume). Pas de `windowEffects` dans `tauri.macos.conf.json` : le matériau natif écrase le rayon choisi. `set_blur` donne aussi à la NSWindow un fond blanc à alpha 0,001, sans quoi le flou déborde des coins arrondis.
- Raccourcis : déclarés une fois dans `defaultShortcuts` (`utils/shortcuts.ts`), d'où se construit Réglages > Raccourcis clavier. Chacun y porte sa rubrique (`group`), son contexte (`when`, sinon toute la fenêtre : sert à détecter les conflits) et son libellé sous la même clé dans `settings.shortcuts.items` d'`en.ts` (vue-tsc bloque s'il manque). Modifiables par l'utilisateur : toujours lus via `useShortcutsStore()` (`matches`, `label`), jamais `defaultShortcuts` ni un `event.key` en dur, Entrée et Échap compris. Hors liste : raccourcis natifs de macOS (⌘Q, ⌘H, copier-coller) et navigation clavier standard (flèches, Échap qui ferme un menu ou annule un glisser).
- Touches comparées sur la lettre tapée (en AZERTY, W n'est pas sur la touche physique `KeyW`). Un raccourci ⌘ porté par un élément du menu natif (`src-tauri/src/menu.rs`) n'atteint jamais la webview. Symboles (⌘, ⌘+ ⌘0) : `also`, `codes` et `shift: 'any'`, car ils demandent ⇧ sur certaines dispositions.
- Messages en bas de fenêtre : `useToastsStore().push({ kind })` (`info`, `success`, `error`), tous dans un seul cadre de verre (`UiToasts`) dont seules les lignes s'animent. Après une action manuelle dont le résultat ne se voit pas (Actualiser, Rétablir), un message dit ce qui s'est passé ; jamais pour une relecture automatique.
- Verre : `.ui-pop` sur le contenu d'un menu ou d'une liste reka (verre posé sur l'enveloppe de reka, qui ne bouge pas ; le contenu grandit depuis son ancrage comme monocode, choix de Jérémy) ou `.ui-glass`. Confirmations et messages : cadre fixe, seul le contenu s'anime (WebKit peint un fond périmé si l'élément flouté est animé). Échap dans un menu reka n'est pas marqué `defaultPrevented` : un écouteur global d'Échap doit ignorer les cibles situées dans un menu.
- Menus d'une ligne (clic droit et bouton « … ») : un seul contenu (`ProjectMenu`, `ShellChatMenu`…) fait de `UiMenuItem`/`UiMenuSub`, posé à la fois dans `UiContextMenu` et `UiMoreMenu` (les parties Dropdown et ContextMenu de reka reposent sur le même Menu). Le menu natif de la webview est coupé dans `main.ts`, sauf dans un champ ou sur un texte sélectionné.
- Listes qui grandissent sans limite (sessions, résultats, archives) : `composables/useProgressiveList.ts` (pages de 40, témoin en bas avec `:key="limit"`), jamais toutes les lignes d'un coup ; recherche en `useDebounced`. Une conversation ne monte que ses 60 derniers messages (`ChatTranscript`), une session fermée au repos quitte la mémoire (`conversations.release`).
- Activité d'un tour (`ChatActivity`, `ChatTool`, `utils/activity.ts`) calquée sur l'app Claude d'après une vidéo de Jérémy : une seule ligne vivante (points CSS, étape en cours gardée jusqu'à la suivante, « {agent} travaille… » seulement sans étape), résumé « Exécuté 4 commandes (1 échec), créé, lu et modifié notes.txt +7 −2 », lignes sans icône, réflexion masquée une fois le tour fini. Fin de tour : copier à gauche, durée à droite (choix de Jérémy).
- Composant dont la racine reka ne rend aucun élément (`DialogRoot`, `HoverCardRoot` : `UiImagePreview`, `ChatThumb`) : `inheritAttrs: false` et `$attrs` sur le déclencheur, sinon les classes passées se perdent sans erreur.
- Recherche des réglages : liste dans `composables/useSettingsSearch.ts`. Une ligne de réglage ajoutée y entre aussi, avec le même `data-setting` sur sa ligne, sinon la recherche mène à la page sans la montrer ; les raccourcis y entrent seuls. Correspondance tolérante maison (`utils/search.ts`, sans lib) : accents, fautes, libellé anglais en repli.
- Transitions des réglages : fondu enchaîné par l'API View Transitions (`crossfade` dans `stores/navigation.ts`). Changer de vue ou de sous-page des réglages passe par `go`, `showSettingsSection` ou `showSettingsDetail`, jamais en écrivant la ref directement : sinon pas de fondu.
- Taille de l'interface : zoom natif de la webview (`setZoom`). Les boutons macOS et les positions du glisser-déposer ne suivent pas : `ShellTitleBar` et `useFileDrop` compensent avec `zoomFactor`.
- Contrôle bordé (bouton secondaire, liste, champ, carte de choix, segmenté) : attribut `data-control`, qui lui donne le relief commun (trait clair en haut, ombre, enfoncement au clic, règle dans `main.css`, choix de Jérémy d'après T3 Code).
- Curseur main et fondu du survol (fond, texte, bordure, opacité en `--hover-duration`, 120 ms) sur tout élément cliquable : règle unique en fin de `main.css`, pas de `cursor-pointer` ni de `transition-colors` au cas par cas. Un bouton révélé au survol reprend `duration-(--hover-duration)` ; un titre recouvert s'estompe (`fade-under-one`/`two`) au lieu de changer de largeur.
- Champ de saisie du chat : un `textarea` au texte transparent posé sur un calque coloré (`ChatPromptText` en `fit`, `.prompt-field`), le même composant qui met les pastilles dans les messages envoyés. Police, padding et retrait se changent sur les deux couches, et le calque ne change aucune largeur (marges négatives, caractère rendu transparent sous une icône) : sinon le curseur se décale du texte affiché, sans erreur.
- `ChatPane` (et son `ChatComposer`) est recréé à chaque changement d'onglet (`:key="tab.id"`) : un état du champ qui doit survivre va dans un store, comme le brouillon (`stores/drafts.ts`, nettoyé à la suppression d'une session et au chargement de la liste).
- Champs de texte : pas de correction ni de suggestions de macOS (choix de Jérémy). `autocorrect`, `autocapitalize`, `spellcheck` et `writingsuggestions` coupés sur `<html>` (`index.html`) et rappelés sur chaque `input`/`textarea` : WebKit ne les hérite pas tous.
- Fichiers glissés depuis le Finder : les événements HTML5 ne les reçoivent pas (Tauri capte le dépôt), passer par `useFileDrop` qui teste la position contre la zone.
- Glisser-déposer des onglets, panneaux et projets de la barre latérale : `composables/useLayoutDrag.ts` (seuil de 4 px, Échap annule, pas de HTML5 drag : Tauri capte le dépôt). Il repère les zones par `data-tab-strip`, `data-tab-id`, `data-pane-index`, `#workspace-area`, `#workspace-column`, `data-group-id`, `data-project-row`, `data-projects-heading` et `data-pinned-heading` : renommer l'un casse le dépôt sans erreur.
- Disposition (panneaux, tailles) mémorisée en localStorage par `stores/layout.ts` : confort local, rien de critique. Une nouvelle valeur par défaut ne touche pas une disposition déjà enregistrée : changer `STORAGE_KEY` pour repartir de zéro.

## Sécurité

- Capabilities ciblées sur `"main"`, jamais `"*"`. Pas de permission `fs:` ni `shell:` exposée au front : tout passe par nos commandes, qui canonisent les chemins sous la racine du workspace.
- Pas de `v-html` sur une sortie d'agent : le markdown passe par `ChatMarkdown` (lexer marked rendu en nœuds Vue). Une XSS dans la webview donne accès aux commandes, donc au lancement de process.
- La webview n'affiche un fichier local que via le protocole asset, limité à `$APPDATA/attachments/**` et `$APPDATA/backgrounds/**` (image de fond, lue aussi en `fetch` pour ses effets, d'où `asset:` dans `connect-src`) : ne pas élargir ce scope, copier l'image dedans.
- CSP définie dans `tauri.conf.json` : ne pas la repasser à `null`, ne pas charger de CDN. Seul domaine externe autorisé : `api.github.com` (vérification des mises à jour).
- `opener` n'ouvre que les pages du dépôt listées dans la capability (releases, issues/new, LICENSE) : élargir ce scope au cas par cas.
