# Architecture Tauri + Vue

Même logique que l'archi Nuxt : depuis un bouton, on retrouve vite la commande Rust puis le service qui fait le travail. Ni repository, ni DTO, ni injection de dépendances. Noms de fichiers en anglais, commentaires en français.

| WebDev / Nuxt | Ici |
|---|---|
| Classe et ses méthodes (`server/services/XxxService.ts`) | `src-tauri/src/services/<domaine>.rs` : `struct XxxService` + `impl` |
| Route API d'un bouton (`server/api/`) | `src-tauri/src/commands/<domaine>.rs` : commande mince |
| `$fetch('/api/...')` | `src/ipc/<domaine>.ts` : wrapper typé autour de `invoke` |
| Schéma Zod partagé (`shared/schemas/`) | struct Rust, type TS généré par ts-rs |
| Variable globale (`gcl...`) | store Pinia |
| Page | `src/views/XxxView.vue` |

```
src/
  views/                    # 1 fichier = 1 écran ; bandeau `// ===== Initialisation =====` pour l'init
  components/<domaine>/     # <Domaine>Xxx.vue
  components/ui/            # UiXxx.vue : nos briques stylées, reka-ui (headless) dessous
  composables/              # useXxx : données réactives + chargement, une instance par appel
  stores/                   # Pinia, un store par domaine, un seul exemplaire partagé
  ipc/                      # seul dossier qui importe @tauri-apps/api
    <domaine>.ts            # 1 fonction = 1 commande Rust
    bindings/               # généré par ts-rs, jamais édité à la main
  i18n/                     # createI18n + choix de la langue au démarrage
    locales/<langue>.ts     # en.ts fait référence, les autres finissent par `satisfies typeof en`
  utils/                    # fonctions pures ; shortcuts.ts = tous les raccourcis clavier ; `*.worker.ts` : Web Worker qui n'appelle que ces fonctions (effets de l'image de fond)
  assets/css/main.css       # Tailwind 4 : jetons de couleur dans @theme, pas de tailwind.config.js
src-tauri/src/
  main.rs                   # n'appelle que nuee_lib::run()
  lib.rs                    # Builder : plugins, manage(XxxService), generate_handler!
  error.rs                  # AppError (thiserror), sérialisé en { kind, message }
  menu.rs, window.rs        # réglages natifs au démarrage : menu macOS, taille de la fenêtre
  commands/<domaine>.rs     # valider, appeler le service (ou la lib si c'est une ligne), répondre
  services/<domaine>.rs     # la logique métier ; un domaine à plusieurs fichiers devient services/<domaine>/mod.rs
  utils/                    # helpers techniques (chemins, env shell)
```

## Pont Vue <-> Rust

- F12 ne traverse pas `invoke` : le nom de commande est une chaîne. Pour s'y retrouver, même nom de domaine partout (`ipc/session.ts` -> `commands/session.rs` -> `services/session.rs`) et commande nommée `<domaine>_<action>` (`session_start`) : un grep sur ce nom trouve les deux côtés.
- Composants, composables et stores n'appellent jamais `invoke` : ils passent par `src/ipc/`.
- La struct Rust est la source de vérité des types : `#[derive(Serialize, Deserialize, TS)]`, `#[serde(rename_all = "camelCase")]` sur tout ce qui traverse l'IPC. ts-rs exporte pendant `cargo test` ; le dossier de sortie se fixe avec `TS_RS_EXPORT_DIR` dans `src-tauri/.cargo/config.toml`.
- Flux continu (sortie d'agent, logs) : un `tauri::ipc::Channel<T>` passé en paramètre de la commande. `emit` seulement pour les notifications rares. Côté Vue, accumuler dans un `shallowRef` et pousser une fois par frame (`requestAnimationFrame`), sinon la réactivité rame.

## Rust

- Commandes `pub` dans leur module, `async` dès qu'elles font des I/O, retour `Result<T, AppError>` dès qu'elles peuvent échouer. Un seul `generate_handler!` dans `lib.rs` : un second appel écrase le premier.
- Pas de `unwrap()` / `expect()` hors démarrage : on remonte une `AppError`.
- État : `std::sync::Mutex` par défaut, celui de tokio seulement si le verrou doit traverser un `.await`. Jamais de verrou tenu pendant un `.await`. Pas d'`Arc` autour de ce qu'on passe à `manage()`, Tauri l'enveloppe déjà.
- Process enfants (CLI d'agents) : le front envoie un id d'agent et des options, jamais une ligne de commande. Rust construit la commande depuis une liste connue, garde le PID et tue par ce PID (`kill_on_drop`).
- Lancée depuis le Finder, l'app n'a pas le PATH du shell : résoudre les binaires d'agents via un login shell.
- Outil absent (Claude Code, gh) : Nuée ne l'installe jamais (choix de Jérémy), « Installer » ouvre sa page officielle par `install_open` (`services/install.rs`, adresse choisie par Rust, ouverte côté Rust hors scope de la capability). En debug, `NUEE_HIDE_BINARIES` fait renvoyer `None` à `find_binary` et masque aussi un chemin choisi à la main.
- macOS : notifications et pastille du Dock par `UNUserNotificationCenter` (`services/notification.rs`), pas `tauri-plugin-notification` (son `NSUserNotification` est refusé par macOS 27) ; lancement au démarrage par `auto-launch` en SMAppService, pas `tauri-plugin-autostart` (son LaunchAgent range l'app en tâche de fond). Les deux exigent l'app empaquetée et signée avec `signingIdentity: "-"` (sinon l'identifiant de signature ne correspond pas et macOS refuse sans demander). Le rebond du Dock (`requestUserAttention` de Tauri) marche aussi sous `tauri dev`, mais macOS ne l'affiche pas quand une autre app est en plein écran.
- Brancher un agent (Codex, Cursor...) : une variante dans `AgentKind`, un `Driver` dans `services/agent/<agent>.rs` (arguments de la CLI, sonde qui liste ses modèles, traduction de sa sortie en `AgentEvent`), son nom et sa commande dans `src/utils/agents.ts` (en le retirant de `upcomingAgents`), son logo dans `assets/agents/` et `SettingsAgentLogo`. Un process par chat gardé ouvert (`services/agent/session.rs`) : messages et interruption écrits sur stdin, relancé avec `--resume` si le mode, le modèle, l'effort, le mode rapide ou le dossier change, arrêté après 5 min sans tour. Chat sur Opus, Fable ou le modèle par défaut : `CLAUDE_CODE_SUBAGENT_MODEL=sonnet` (`session_env`) ; effort Élevé ou plus : `CLAUDE_CODE_SUBAGENT_EFFORT=medium`. Jamais si l'utilisateur a posé la variable lui-même. Relancer le process après 5 min ne casse pas le cache d'une heure (mesuré dans les transcripts : quelques centaines de tokens réécrits). Il démarre dès le focus du champ de saisie (`agent_warm`).
- Réglages > Agents : la liste sur la page, les réglages de chaque agent dans sa sous-page (`settingsDetail` = son `AgentKind`). `stores/agents.ts` garde, par agent, l'activation, le chemin choisi à la main et les réglages de départ d'un nouveau chat (repris par `conversations.blank`). Statut par `agent_probe`, comme T3 Code : la CLI lancée sans tour répond à `initialize` (version, compte, modèles) puis `get_usage` (quotas ; `skip_behaviors`, sinon elle parcourt tout l'historique local). Jamais de lecture du jeton ni du Trousseau. Dernière version sur npm (`dist-tags`, selon `autoUpdatesChannel` ou le cask Homebrew), mise à jour par `claude update`. Un chemin choisi à la main doit se nommer comme l'agent, et sert ensuite à tous ses chats. Un tour qui contredit le compte affiché relance la sonde. Pendant un tour, les `rate_limit_event` du flux (événement `usage`) mettent les quotas à jour ; celui d'un modèle (Fable) n'y est pas nommé, la sonde donne son nom. Interrupteur Hooks : `hooks` dans `SessionSpec`, `--settings {"disableAllHooks":true}` quand il est coupé (tous les hooks, garde-fous compris) ; le changer relance le process au tour suivant.
- Réglages > Skills et MCP : config globale de Claude Code seulement (ceux d'un projet iront sur sa future page Projet, choix de Jérémy). Les interrupteurs de la liste ne valent que pour Nuée ; la sous-page d'un skill (`skill:<dossier>`) ou d'un serveur (`mcp:<nom>`) laisse choisir Nuée seulement ou Partout, repart sur Nuée à chaque ouverture et signale Partout en rouge (choix de Jérémy). Nuée seulement : gardé dans `stores/skills.ts`, envoyé dans `SessionSpec` (`skills`, `serversOff`) et passé en `--settings` ; un skill coupé partout peut y être rallumé, pas un serveur (`deniedMcpServers` s'additionne). Partout : `services/agent/settings.rs` écrit le `settings.json` (`skillOverrides` dont la clé est le nom du dossier, pas le `name:` du SKILL.md ; `deniedMcpServers`, seul réglage qui coupe un serveur de toutes ses portées), ordre des clés et droits gardés. Pas de création de skill à la main : « Nouveau skill » et « Modifier avec l'IA » (`composables/useSkillChat.ts`) ouvrent un chat dont Nuée affiche elle-même le formulaire (élément `command`, sans tour d'agent) ; la `ChatCommand` part avec la première réponse, Rust y ajoute les consignes de `services/agent/skill_writer.md` (tirées du skill `j-create-skill` de Jérémy) avec les vrais chemins. Formulation toujours identique (choix de Jérémy) : l'IA finit par un seul bloc `nuee-skill` (JSON) que `ChatSkillResult` met en forme ; le texte affiché vient de l'i18n, jamais de l'IA. Skills relus à chaque ouverture du menu « / » du composer ou de la page, pas de surveillance du dossier ; la CLI voit un skill créé sans relancer sa session. État des serveurs : la CLI lancée sans tour répond à `mcp_status`, redemandé jusqu'à ce qu'aucun ne soit en connexion et au moins 2 s (les serveurs de plugins arrivent tard). Les connecteurs du compte claude.ai (`McpServer.connector`, scope `claudeai` ou nom `claude.ai …`) sont listés à part, ceux ni connectés ni en connexion repliés en bas (« Non connectés », demande de Jérémy : un compte en a souvent beaucoup), avec l'interrupteur Nuée seulement des serveurs mais sans sous-page Partout, et le volet Session ne montre que ceux branchés et actifs pour Nuée : « Connecter » ouvre leur page sur claude.ai (`mcp_open_connectors`, adresse fixée par le driver), jamais `mcp_authenticate`. Connexion OAuth par `mcp_authenticate` une fois le serveur listé, jamais `claude mcp login` qui exige un terminal ; un serveur revenu est retenté dans les chats ouverts (`mcp_reconnect`). L'aperçu et l'éditeur d'un SKILL.md s'ouvrent dans le panneau de droite de `App.vue` (même poignée et largeur `layout.right` que celui des chats), jamais dans un panneau propre à la page.
- Réglages > Intégrations : GitHub par la CLI `gh` seulement, lancée par Rust (`services/github.rs`). Jamais sa config ni le Trousseau, jamais `gh auth token` (aucun jeton dans l'IPC, un log ou le disque), jamais `logout`, et `switch` seulement sur le bouton « Rendre actif » (il change gh dans tous les terminaux, d'où le refus d'un compte que gh ne liste pas comme utilisable). `gh auth status --json hosts` est lu même avec un code de sortie non nul ; `unknown flag: --json` = gh trop ancien, pas « déconnecté ». L'interrupteur d'un compte ne vaut que pour Nuée (`stores/integrations.ts`, clé `hôte/login`, tous activés par défaut). Page en cartes de services comme Réglages > Agents, sous-page `github` pour les comptes. Avatars : `https://github.com/<login>.png` lu par Rust sans jeton et passé en `data:` (la CSP n'autorise aucune image distante). Ajout d'un compte : `gh auth login --web` sans `--git-protocol` (gh l'écrirait pour tous les comptes) et sans terminal (stdin nul), qui écrit code et URL sur stderr sans attendre de touche ni ouvrir de navigateur ; Rust les passe par `Channel`, ouvre la page sur « Ouvrir GitHub » par `tauri_plugin_opener::open_url` (côté Rust, hors scope de la capability) et annule par le PID. Le compte ajouté devient l'actif de gh (comportement de gh, signalé dans l'interface).
- Mise à jour d'un agent : carte `AgentUpdateNotice` (en haut à droite, les messages occupent le bas), fermée jusqu'au prochain lancement seulement (en mémoire, comme monocode), qui annonce elle-même le succès ou l'erreur (`agents.update(kind, false)` sans message en bas). Quota passé 80 % : `ChatLimitSoon` au-dessus du champ d'une conversation lancée, fermé pour la fenêtre de quota (remise à zéro arrondie à l'heure, elle varie d'un relevé à l'autre).
- Connexion du compte d'un agent (`services/agent/login.rs`, `AgentLogin.vue`, dans l'erreur d'un message et Réglages › Agents) : `claude auth login` sans terminal ouvre la page de connexion et attend sur stdin le code `code#état` que la page affiche (pas de retour sur localhost, essayé). Rust garde l'adresse, le front envoie le code, Rust l'écrit sans le journaliser. Lancée sous `tauri dev` depuis un terminal, la CLI peut entourer l'adresse d'un lien OSC 8 : la couper au premier caractère de contrôle. Les process ouverts sans compte sont retirés une fois connecté.
- Mode Auto : les demandes d'autorisation passent par `--permission-prompt-tool stdio` (`control_request` `can_use_tool`) et s'affichent dans `ChatApproval` ; Rust garde les paramètres de l'outil pour les renvoyer avec l'accord. Les questions de Claude (`AskUserQuestion`) arrivent par le même `can_use_tool` (en Bypass aussi d'après monocode, pas encore essayé sur la CLI) : `Approval.questions` les porte, `ChatQuestion` les pose une page à la fois, `agent_answer` répond `allow` avec `answers` (texte de la question → libellés joints par « , ») dans `updatedInput`, ou `deny` si tout est passé. Pas de consigne système ajoutée à Claude : une phrase en anglais en fin de prompt le fait répondre en anglais.
- Message envoyé pendant une réponse (Réglages › Général) : ↵ suit le réglage, ⌘↵ (`sendOther`) fait l'autre choix, comme l'app Claude, et le champ l'annonce. En file côté front (`conversations.queue`, un par tour, retenue après un arrêt), ou `agent_steer` qui l'écrit sur stdin pendant le tour ; la CLI le lit à sa prochaine étape, dans le même tour (essayé). Refusé une fois `answered` reçu : il repasse en file. Limite d'utilisation : `rate_limit_event` au statut `rejected` donne l'événement `limited` ; le front renvoie un message à l'heure de remise à zéro, minuterie non persistée.
- Fin de tour en deux temps : `answered` dès que la réponse est complète (le front pose la ligne de fin de tour), `turnEnd` quand l'agent a fini de ranger (résumé, hooks : plusieurs secondes). Un message envoyé entre les deux attend `turnEnd`. Après un arrêt, le texte coupé est rappelé à l'agent si son process est neuf (paramètre `recap`).
- Sous-agents (`ChatSubagent`, modèle monocode) : leurs lignes `parent_tool_use_id` ne remontent qu'en `TaskStep` (outils appelés et leur issue, rangés dans `task.steps` de l'outil Agent), jamais leur texte. Ils restent hors du pli d'activité. Un tour rouvert par l'agent commence par un repère `resume`.
- Entre deux tours, la session garde le canal du dernier tour (`listener` dans `services/agent/session.rs`) : tâches de fond qui avancent, et tour que Claude rouvre seul quand l'une finit (`turnStart`). Le process n'est pas arrêté pour inactivité tant qu'une tâche tourne. Une requête qui attend sa réponse (rewind) passe par `Session::request`, la `control_response` est routée par son `request_id`.
- Flags de chat Claude non documentés, essayés sur la CLI : `--thinking-display summarized` (sans lui la réflexion arrive vide), `--replay-user-messages` (l'`uuid` de chaque message devient `agentId` sur l'élément `user`), `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=1` pour `rewind_files`, puis `rewind_conversation` (`target_message_uuid`, coupe tenue après `--resume`). `tool_use_summary` écarté exprès : un appel de modèle par série d'outils, l'app Claude ne l'affiche pas. Mode rapide : `fastMode` dans `--settings`, sans quoi la CLI le refuse (`sdk_opt_in_required`) ; seuls les modèles `supportsFastMode` le servent, `catalog.resolve` le coupe ailleurs.
- Jauge de contexte : `control_request` `get_context_usage` (non documenté, même calcul que `/context`, répond sans tour ni connexion), pas la somme des `usage` du flux. Relevé à chaque `turnEnd` et juste après une compaction (id `nuee-context`, revient en événement `context`) et rendu par `agent_warm` ; gardé en base avec le chat (colonne `context`).
- Compaction (essayé, CLI 2.1.296) : `system/status` `compacting`, puis `compact_result` (`failed` + `compact_error`), puis `compact_boundary` (`pre_tokens`). « Après » vient du relevé du contexte, pas de `post_tokens` (messages seuls). La CLI ne renvoie pas `/compact` mais un message `<local-command-stdout>`, ignoré ; `/compact` part seul, sans rappel ni consignes devant, sinon elle ne le reconnaît pas. Compaction en veille, comme T3 Code (Réglages › Général, `idleCompaction`) : la CLI donne la durée de son cache à chaque `result` (événement `cache`, `ephemeral_1h` ou `5m`) ; une session ouverte de 200K tokens ou plus, inactive, reçoit `/compact` 2 min avant la fin du cache d'une heure. Celle de la CLI ne tourne pas ici, le process est arrêté après 5 min.
- Modèles et efforts : jamais codés en dur, l'agent installé les décrit (Claude : `control_request` `initialize`, lu une fois par lancement puis à chaque sonde de Réglages > Agents). L'interface montre toujours une valeur réelle (« Opus 5.5 », « Moyen »), jamais « par défaut » seul (l'entrée « Par défaut » des menus du projet affiche à droite ce qu'elle donne). Effort par défaut : Moyen pour tous (choix de Jérémy), fixé par le driver (`Catalog.default_effort`), jamais lu dans `settings.json` ; priorité session > projet > Réglages › Agents > Moyen, et un modèle sans Moyen prend le plus proche, le plus bas à égalité (`catalog.resolve`). Anciens modèles (`ModelInfo.legacy`, repliés dans le sélecteur) : décidé par le driver, chez Claude ceux que la CLI nomme par leur identifiant complet (`claude-opus-4-8`) plutôt que par leur famille (`opus`). Modes de permission (choix aussi par projet, `Project.mode`) : Bypass, Auto et Demander (`ask`, `--permission-mode default` : chaque modification ou commande passe par la carte d'autorisation ; Auto accorde seul ce qu'il juge sûr, donc la carte s'y voit rarement), passés en flag à chaque tour : ils priment sur la config Claude de l'utilisateur.
- Pièces jointes vers Claude : images en bloc base64 (la CLI redimensionne), autres fichiers en `@"chemin"` placé avant le message. Pas d'image en `@` : au-delà de ~3 Mo, elle est ignorée sans erreur.
- Terminal (`services/terminal.rs`, `stores/terminals.ts`) : un pty par shell, rangé sous l'id du chat, dans le même dossier que son agent. Les instances xterm restent en mémoire hors du DOM (historique gardé), posées par `attach(clé, zone)`. Fermer l'onglet du chat ou recharger la page tue ses shells (`on_page_load`) : `touch src/main.ts` en dev repart sans terminal.
- Bloc de code (`ChatCodeBlock`) : sans langue ou en `text`, `txt`, `plaintext`, `markdown`, `md`, il revient à la ligne (une cale flottante laisse la place aux boutons du coin) ; le vrai code défile. Bouton Lancer d'un bloc de code (`ChatCodeBlock`, `utils/shellCommand.ts`, `stores/codeRuns.ts`), comme l'app Claude : seulement sur un bloc shell d'une seule commande d'une réponse finie, et lancé sur un clic, jamais seul. `terminal_run` : même pty et même service que le terminal (shell de connexion en `-ilc`, refus d'un chat absent de la base), arrêt par `terminal_stop` (SIGTERM, SIGKILL après 3 s), tué avec les shells du chat. La sortie reste à l'affichage, jamais envoyée à l'agent, gardée en mémoire tant que la session a un onglet ; couleurs ANSI lues par `utils/ansi.ts` en nœuds Vue. « Reprendre dans le terminal » (`terminals.paste`) ouvre le volet et dépose la commande à l'invite du shell actif sans l'exécuter (shell absent ou occupé : un nouveau, attendu jusqu'à son invite) ; collée par `term.paste`, entre crochets si le shell le gère, caractères de contrôle retirés ; sur plusieurs lignes sans collage entre crochets, rien n'est déposé.
- Explorateur (volet `files`, `services/files.rs`, `stores/files.ts`, `components/files/`), modèle monocode : l'arbre lit un dossier à la fois (`files_dir`, ignorés par git masqués), jamais `git ls-files` (2 s sur un gros dépôt) qui ne sert qu'à la recherche ; le dossier est surveillé par `notify` tant que le volet est monté (`files_watch`), pas de bouton Actualiser. Le front n'envoie que des chemins relatifs, bornés par `resolve` ; un worktree venu du front passe par `worktrees.enter`. Fichiers ouverts à gauche de l'explorateur. Comme T3 Code, leurs onglets montent dans la barre de titre au-dessus de l'éditeur (Teleport de `FilesEditorPane` vers `#dock-editor-tabs`, rendu tant que le panneau est ouvert : un Teleport ne cherche sa cible qu'à sa création) ; dessous, la ligne d'outils du fichier (`FilesViewer`) tient celle de l'arborescence, même hauteur et même trait : fil d'Ariane (dossier de la session, puis dossiers et nom ; à la racine, le dossier seul, le nom est dans l'onglet ; un clic montre l'élément dans l'arbre), enregistrement, « … » (`FilesMenu`, dont l'entrée à cocher « Aperçu » d'un markdown : bascule globale `store.view`, et l'ouvre en aperçu depuis l'arbre ; un SVG reste en aperçu, sans bascule). Images (et SVG en aperçu) : `FilesImage`, même bandeau pour toutes ; pendant la lecture, l'image précédente reste, indicateur après 200 ms. Panneau partagé côte à côte : les onglets restent dans le volet (`layout.spans`). Le trait entre les deux colonnes monte jusqu'en haut de la barre de titre (choix de Jérémy) : `ShellTitleBar` le trace à `editorWidth` et l'allume avec la poignée `data-explorer-handle`.
- Serveurs du projet (`services/server.rs`, `stores/servers.ts`) : `.claude/launch.json` du dossier de la session (format de l'app Claude, JSON à commentaires), relu à chaque ouverture du menu et en fin de tour de la session. Le front n'envoie que le nom, Rust relit la commande. Un pty par serveur, rangé par dossier et nom (deux sessions du même dossier partagent les mêmes), un seul `Channel` pour tous (`server_watch`, rebranché au rechargement de la page, qui ne les tue pas). `autoPort` absent = port libre comme `true` (l'exception npm de l'app Claude n'est pas reprise). Arrêtés à la fermeture de l'app (SIGTERM, SIGKILL après 2 s). Pas d'éditeur du fichier : « Ajouter un serveur » envoie la demande à l'agent dans la session (`drafts.request`, repris par `ChatPane.send`), comme l'app Claude où l'agent écrit lui-même le fichier.
- Navigateur (`services/browser/`, `stores/browser.ts`, `components/browser/`) : une WKWebView par onglet créée en objc2 (`native.rs`) et posée au-dessus de la webview de Nuée, pas une webview Tauri (le mode `unstable` change la fenêtre principale ; ici la page n'a aucun accès aux commandes). macOS seulement, les autres OS échouent proprement. Le front donne la zone du volet (`browser_place`, px × `zoomFactor`, numéro de pose croissant : les commandes async arrivent dans le désordre, une pose dépassée est ignorée, sinon la page reste par-dessus Nuée) ; rien de Nuée ne passe par-dessus, `BrowserPage` remplace la page par sa capture (décodée et peinte avant de cacher la page) quand un menu, un message ou une modale la recouvre. L'agent n'ouvre jamais le volet (comme l'app Claude et T3 Code) : sa page entre dans les onglets et une pastille dit qu'il agit. Console, réseau et raccourcis ⌘ viennent de `page.js` (monde de la page) par `webkit.messageHandlers.nuee` ; les outils de l'agent (`agent.js`, refs `ref_N`) tournent dans le monde `nuee`, retenu par l'onglet (WebKit détruit un monde lâché, et les refs avec). Clics et touches : vrais `NSEvent` envoyés à la vue. Stockage par projet (`data_store_identifier` = hash du dossier du projet). Claude pilote par le serveur MCP `nuee` de type `sdk` (`tools.rs`) : `--mcp-config` + `--allowedTools mcp__nuee`, les `control_request` `mcp_message` sont lus dans `session.rs` et répondus sur stdin, sans port ; le texte `instructions` du serveur porte la vérification après modif, comme l'app Claude (activée par défaut, l'agent ne vérifie que ce qui se voit dans le navigateur ; confirmé par Jérémy, pas « sur demande seulement »), toujours envoyé (sauf `"autoVerify": false` dans `.claude/launch.json`) : la CLI ne renvoie pas des consignes changées en cours de session, et l'agent écrit souvent `launch.json` lui-même.
- Sessions pilotées par l'agent (`services/operator.rs`, `stores/operator.ts`) : outils `list_sessions`, `read_session`, `start_session`, `send_message`, `rename_session`, `archive_session` du serveur MCP `nuee`. Projets et sessions vivent côté front : Rust émet `operator-request`, le front exécute et répond par `operator_reply` (60 s au plus). Une session lancée s'ajoute à la liste sans onglet (`workspace.addChat`) et prévient celle qui l'a lancée à chaque fin de tour, 3 fois d'affilée au plus sans message de l'utilisateur (deux agents se répondraient en boucle). Lien parent en base (`parent_id`) : la liste imbrique la session sous la plus haute de ses ancêtres visibles (`workspace.nestedChats`, `ShellChatGroup`), sauf épinglée. Un message d'une autre session porte `from` sur l'élément `user` : l'agent reçoit le texte précédé de « [Nuée] … » (`agentPrompt`), la conversation l'affiche comme l'app Claude (`ChatSessionMessage`) : « Message reçu de » et le texte atténué dessous, ou, pour la consigne de départ (`from.task`), « Démarrée par … depuis … » et la carte « Tâche » (`ChatTaskCard`), carte que la session lanceuse montre aussi à la place de l'outil `start_session`, hors du pli d'activité.
- Chat sans projet : Rust le lance dans `<données de l'app>/scratch/<id du chat>`, supprimé avec le chat.
- Worktrees (`services/worktree.rs`, git toujours avec `-c core.fsmonitor=false`) : le sien, créé par `agent_send` au premier message dans `<données de l'app>/worktrees/<id du chat>` sur `nuee/<8 premiers caractères de l'id>`, à partir de la branche de départ choisie (`worktreeBase` de `SessionSpec`, gardée en mémoire dans `stores/worktrees.ts` jusqu'à l'envoi ; sinon HEAD) ; ou un worktree du dépôt rejoint par plusieurs sessions, créé dans la sous-page `worktrees:<id du projet>` (`worktrees/<id du projet>/<branche nettoyée>`). Le chemin est en base (`worktree_path`), jamais déduit de l'id ; un chemin venu du front n'est utilisé que s'il est dans `git worktree list`. Supprimer une session retire son propre worktree s'il est propre et que personne d'autre ne l'utilise ; supprimer un worktree est refusé s'il a des changements, et ses sessions repartent dans le dossier du projet (`--resume` y retrouve la conversation). La branche reste toujours, jamais `--force` (choix de Jérémy, comme T3 Code). Après le premier message, l'endroit ne change plus dans la session (simple rappel `ChatPlaceInfo`, choix de Jérémy), ni la branche d'un worktree ; celle du dossier du projet se change depuis Environnement ; un worktree partagé se rejoint par « Nouvelle session ici » dans Réglages › Worktrees. git répond dans la langue du système : ne jamais tester son message d'erreur, seulement les fichiers qu'il cite en retrait.
- Volet Git (identifiant interne `changes`, `components/git/`, `services/worktree.rs`), modèle monocode et VS Code : deux modes dans le volet, Changements et Historique (icônes à bascule à droite de sa ligne d'outils, toujours présente, état vide compris, gardée d'un mode à l'autre pour ne pas perdre le focus ; mode par projet dans `layout.right.gitModes`). Actions rapides en petit à droite de la ligne de la branche, comme monocode : tout annuler et actualiser (Changements), rechercher et actualiser (Historique). Mise en page de monocode : branche (`GitBranchRow`, commune aux deux modes), liste, puis champ et bouton de commit en bas (demande de Jérémy), sur une même marge de 8 px. Le bouton de commit a le cadre et la hauteur du champ, pas le fond d'accent (demande de Jérémy : il ne doit pas peser plus que le champ). État par session (message, onglets de diff) dans `stores/gitPanel.ts` ; liste, diffs lus et commentaires dans `useGitChanges`, une instance par volet partagée par `provide`. Changements : branche (menu de `useSessionBranch`, commun avec Environnement), champ de message (⌘↵ = `sendOther`, une à trois lignes), fichiers à plat (nom, dossier atténué), état en lettre colorée. Pas d'indexation (choix assumé : la liste est un diff contre HEAD, les agents indexent eux-mêmes, un vrai système demanderait deux listes et deux diffs par fichier) : le commit direct emporte tout, non suivis compris, sauf un dépôt git imbriqué (entrée `sous/` de `ls-files`, que `add` changerait en lien vers un autre dépôt : exclu du `add`, signalé). Commit direct = `worktree_commit` (`add --all` puis `commit --message=…`, refus d'un message vide ou d'une liste vide), push direct = `worktree_push` (jamais forcé ; vers la branche suivie lue par `for-each-ref`, `push <dépôt> HEAD:<sa branche>` : `push.default`, `pushRemote` et `remote.*.push` de l'utilisateur ne s'appliquent pas ; sans branche suivie, `push --set-upstream` vers `origin` ou le seul dépôt distant, erreur claire sinon) : faits par l'app (`gitActions.commitNow`), refusés pendant une action de fond du même dossier (`runs`) qui refuse à son tour de démarrer pendant ce temps (`manual`) ; ils posent le même séparateur `git` dans le fil. Un seul bouton Commit, comme T3 Code (demande de Jérémy : pas de skill dans ces menus, il les invoque dans la conversation) : champ rempli, ce message ; vide, l'action de fond `message` (Haiku via `economy`, consigne qui fait lire le SKILL.md du skill de commit sans le lancer) écrit le titre puis `commitNow` committe (`commitAfter`). « Générer le message » (étincelle) met seulement le titre dans le champ. Push direct à côté du pull, actif s'il reste des commits à pousser. Diff à gauche de la liste comme l'éditeur de l'Explorateur (`useDockEditor`, même largeur de liste `files.explorerWidth`, `layout.setEditing` par volet, mêmes onglets : `utils/editorTabs.ts` et `ShellEditorTabs`, téléportés dans `#dock-editor-tabs`), changement suivant par `data-change` de `ChatDiff` ; panneau partagé (même empilé : sinon la largeur d'édition fait basculer côte à côte puis empile) ou fenêtre trop étroite (`room` < 560 px) : dépliage sous la ligne. Pull direct (`worktree_pull`, `--ff-only` : jamais de fusion ni de rebase, refusé si les branches ont divergé) sur la ligne de la branche et dans Environnement, avec une pastille quand `worktree_behind` (fetch discret, une fois par minute au plus, `sessionGit.checkBehind`) trouve des commits à récupérer. Annuler un fichier (`worktree_revert_file`) ou tout (`worktree_revert_all`, qui reçoit la liste confirmée et n'annule que ses chemins encore présents : un fichier créé entre-temps reste) remet dans l'état de HEAD, chemin accepté seulement s'il est dans la liste des changements (un non-suivi est supprimé du disque, un dépôt imbriqué laissé et signalé), confirmation rouge, boutons désactivés pendant une action de fond ou un commit direct du dossier. Commandes qui écrivent (`write_dir` de `commands/worktree.rs`) : refus d'une session absente de la base ou dont le propre worktree n'est pas encore créé. git trop long (`run`) : SIGTERM, SIGKILL 3 s après (tué net, il laisserait `index.lock`). Commentaires sur les lignes d'un diff non commité (`stores/diffComments.ts`, en mémoire, par session), partis ensemble dans un seul message. Bouton Actualiser discret (demande de Jérémy) en plus de la relecture automatique : à l'ouverture, en fin de tour, après une action, au retour de la fenêtre, quand le pointeur entre dans le volet et quand l'Explorateur voit le disque changer (au plus toutes les 2 s, diffs montrés relus sans être vidés). Historique : recherche ouverte par le bouton de la ligne de la branche, champ dessous, `worktree_log` (50 par page, `next` pour la suite ; recherche faite en Rust sur le titre seul, `to_lowercase` pour la casse et les accents, journal lu par lots jusqu'à 50 trouvés ou 2000 commits lus : une page peut revenir vide avec une suite, que le témoin du bas demande aussitôt ; doublons écartés à l'ajout), `worktree_commit_files` et `worktree_commit_diff` (identifiant hexadécimal seulement, comparé au premier parent), lecture seule. État git dans `stores/sessionGit.ts`, relu par `ChatPane` entre deux tours, au retour de la fenêtre et à l'ouverture d'Environnement et du volet. Avant le premier message, le volet lit déjà le dossier où la session va travailler (celui du projet ou le worktree rejoint, comme l'Explorateur) ; nouveau worktree pas encore créé : une phrase à la place ; commit, actions de fond, « Initialiser Git » et commentaires attendent le premier message (désactivés, infobulle), l'annulation reste permise. Dossier du projet hors git (`projects.support` à `notRepo`, relu à l'ouverture d'Environnement, en fin de tour et en fin d'action) : la partie git d'Environnement devient une ligne « Initialiser Git », le volet garde ses deux modes et propose le même bouton.
- Actions git (`stores/gitActions.ts`, `useGitActions` pour état et choix des deux volets, `ChatGitRun` pour la ligne en cours), fonction de l'interface comme le mode Orchestre (choix de Jérémy, d'après T3 Code) : commit, push et pull faits par l'app ; seuls le message de commit et « Initialiser Git » passent par une session de fond ; jamais un message de l'utilisateur ni un tour dans le fil d'origine. Réussie, elle y pose un séparateur (élément `git`, lu par git : titre du commit, branche, `origin`) ; au message suivant de l'utilisateur, `conversations.gitNote` met devant le texte transmis (pas la bulle) une note « [Nuée] Depuis ton dernier message… » (`operator.git`), une seule fois (`told` enregistré), jamais devant une commande « / ». Un clic lance une session de fond (`workspace.addChat` avec `parentId` et `background`, colonne en base) dans le même dossier et worktree, même agent, mêmes options (mode d'autorisation compris), qui reçoit la consigne de `gitActions.prompts`, ou pour « Initialiser Git » le skill de l'utilisateur dont le nom contient « init » et « repo » (`skills.actionSkill`) suivi de `gitActions.go` (un clic vaut accord). Modèle (`economy`) : le moins cher que l'agent propose (`CHEAP`, alias exact avant libellé), à son effort le plus bas. Les actions `ship` et `commitPush` ne restent que pour lire les séparateurs déjà enregistrés. Conversation d'origine pas encore chargée : action refusée par un message, sinon la session de fond prendrait les réglages du projet, peut-être plus larges. Une action à la fois par dossier (clé de `runs`). Cachée (`workspace.hidden`, en mémoire : hors liste, recherche, outils de sessions et `attention`) tant qu'elle se déroule seule ; le bouton montre l'étape (commande git reconnue, sinon `lastStep`), le temps écoulé et ■. Fin : tour fini et état git conforme (relu, pas le texte de l'agent) : session supprimée (une archive garderait le worktree d'origine). Messages toujours écrits par l'app, jamais repris de l'agent (choix de Jérémy) : titre par action, corps lu par git (`worktree_head` : « titre du commit · branche », ou l'adresse d'`origin` sans identifiants pour un dépôt créé) ; attente : « Une réponse est attendue » et le nom de l'action ; l'erreur brute seulement pour un échec, deux lignes au plus (`clamp`). Question, autorisation, échec, arrêt après un début de travail ou état git non conforme : la session est révélée sous celle d'origine, message « Ouvrir » (gardé tant qu'elle attend). Révélée, c'est une session comme une autre. Après un redémarrage ou un rechargement, une action interrompue réapparaît sous sa session d'origine ; `background` en base l'empêche toujours de rendre compte à l'agent d'origine.
- Archives : colonnes `archived` et `archived_at`, la session quitte l'historique et la recherche, Réglages › Archives la restaure ou la supprime. Suppression automatique côté front (`workspace.purgeArchives`, au lancement puis toutes les heures, délai dans `stores/general.ts`) pour passer par `deleteChat` et son ménage (worktree, scratch, pièces jointes). La recherche des archives lit le texte des messages par `chat_archived_texts` (JSON des items lu en SQL). Dans l'interface, on dit « session », jamais « chat » (choix de Jérémy) ; l'endroit des sessions sans projet s'appelle « Sans projet » (icône `NoProject`, un portable, comme l'app Claude). Les clés i18n et le code gardent `chat`.
- Historique : SQLite (`services/chat.rs`), une ligne par chat ; les messages sont un JSON que seul le front lit. Un chat n'entre dans l'historique qu'à son premier message (`started`). Fermer un onglet garde le chat (`layout.tabs` = onglets ouverts, `tabs` = tous les chats), sauf s'il n'a jamais servi ; sinon seule la corbeille de la barre latérale le supprime. Nouvelle colonne = nouvelle entrée dans `MIGRATIONS`, jamais une modif d'une entrée passée. La liste des sessions ne charge jamais les messages : ce qu'elle affiche (modèle, `added`/`removed`) est recopié dans `chats` à chaque `chat_save`, compté par le front (`sessionDiff`).

## Textes et langues

- Aucun texte d'interface en dur : la clé va dans `src/i18n/locales/en.ts`, puis traduite dans toutes les autres langues. vue-tsc bloque si une traduction manque, mais pas si `t('...')` cite une clé qui n'existe pas : la copier depuis `en.ts`.
- Aucun nom d'agent ni de service en dur dans un texte générique : `{agent}` (`agents[kind].name`), ou une formule neutre (« tes agents », « tes comptes connectés »). Nuée branchera plusieurs agents et services (choix de Jérémy) ; seule la page d'un service précis (GitHub) le nomme.
- `@` dans un texte i18n ouvre un lien vers une autre clé et casse la compilation : l'écrire `{'@'}`, dans une chaîne entre guillemets doubles.
- Traductions précompilées au build (`@intlify/unplugin-vue-i18n`, compilateur retiré du bundle) : un texte chargé à l'exécution (API, fichier) ne sera pas interprété en production.
- Langue du système : la commande Rust `system_locales`, jamais `navigator.language` (WebView2 renvoie toujours en-US). Dates et nombres : `Intl.*` avec la locale de vue-i18n, jamais `undefined`.
- Marges et positions en propriétés logiques Tailwind (`ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`) plutôt que gauche/droite : ça garde la porte ouverte aux langues écrites de droite à gauche.

## Interface

- Infobulle sur un bouton qui ouvre un menu ou un popover reka : `UiTooltip` autour du `*Root`, jamais entre le `Root` et son `Trigger` (contexte Popper injecté au plus proche : le menu se cale sur l'infobulle et reste hors de l'écran, sans erreur). Voir `UiMenu`.
- Menu reka non modal : `useMenuToggle` (retient s'il était ouvert à l'appui sur le déclencheur), sinon un clic sur sa flèche ouverte le ferme (clic « dehors ») puis le rouvre aussitôt.

- `UiTooltip` autour d'un élément qui porte son état en `data-state` (radio, interrupteur) : le trigger de l'infobulle écrase cet attribut, styler l'état choisi sur `aria-checked`. - Couleurs uniquement via les jetons de `main.css` (`canvas`, `chrome`, `surface`, `popover`, `content`, `muted`, `stroke`, `selection`, `accent`, `signal`, `signal-text`, `on-signal`, `ring`, `stroke-focus`, `edge-hover`, `danger`, `success`, `warning`, `info`, `orange`, `violet`, `skill`, `mention`). - `warning` (ambre) : ce qui demande un geste sans être une erreur (autorisation ou question en attente, compte non connecté, outil absent ou trop ancien, limite proche, fichier modifié ailleurs, changements non commités).

Champ de saisie : gabarit `field` (cadre, `data-control`) et `fieldText` (le champ) de `components/ui/field.ts`, 28 px, texte 12 px ; sa bordure passe à `stroke-focus` (gris à peine plus clair, comme monocode), pas d'anneau. ## Sécurité

- Capabilities ciblées sur `"main"`, jamais `"*"`. Pas de permission `fs:` ni `shell:` exposée au front : tout passe par nos commandes, qui canonisent les chemins sous la racine du workspace.
- Pas de `v-html` sur une sortie d'agent : le markdown passe par `ChatMarkdown` (lexer marked rendu en nœuds Vue). Une XSS dans la webview donne accès aux commandes, donc au lancement de process.
- La webview n'affiche un fichier local que via le protocole asset, limité à `$APPDATA/attachments/**` et `$APPDATA/backgrounds/**` (image de fond, lue aussi en `fetch` pour ses effets, d'où `asset:` dans `connect-src`) : ne pas élargir ce scope, copier l'image dedans.
- CSP définie dans `tauri.conf.json` : ne pas la repasser à `null`, ne pas charger de CDN. Seul domaine externe autorisé : `api.github.com` (vérification des mises à jour).
- `opener` n'ouvre que les pages du dépôt listées dans la capability (releases, issues/new, LICENSE) : élargir ce scope au cas par cas.
